# CQA · Conversation Quality Analytics — Freedom Broker (команда DealDucks)

Прототип оценки работы оператора по чек-листу. Идея — **«разбор шахматной партии»**: строгая оценка по
чек-листу (балл, обоснование, дословная цитата для каждого критерия) плюс наглядный слой поверх неё —
знаки ходов `!! ! ?! ? ??` у каждой реплики оператора, «лучший ход» для ошибок и кривая настроения клиента.
Переключатель **«Строгий режим»** оставляет только таблицу критериев — для бизнес-пользователей и Dynamics 365.

## Запуск (1–2 команды)

Нужен Python 3.10+.

```bash
# Windows
run.bat
# macOS / Linux
./run.sh
```

Скрипт создаёт виртуальное окружение, ставит зависимости, при первом запуске создаёт `.env` из `.env.example`
и открывает http://localhost:8000. В `.env` нужно вписать ключ модели и ссылку на API организаторов:

```env
OPENAI_API_KEY=sk-...           # оценка критериев (gpt-6.1-sol)
GEMINI_API_KEY=...              # «разбор партии» (gemini-3.8-flash), ключ Google Cloud Agent Platform
CQA_API_URL=https://...invoke?api-version=1&sp=...&sig=...   # ссылка GET из задания
```

Вручную: `pip install -r requirements.txt && python -m backend.app`.
При старте набор `DEFAULT_GROUP_ID` (DEV) загружается автоматически. Запросы к API организаторов идут
только через бэкенд (CORS).

## Модель и стоимость

| Что | Модель | Вызовов на диалог |
|---|---|---|
| Оценка критериев | `gpt-6.1-sol` (OpenAI), reasoning_effort=medium, строгая JSON-схема | 8 (по одному на критерий) + до 2 повторов, если цитата не найдена |
| Разбор партии и настроение клиента | `gemini-3.8-flash` (Google Cloud) | 1 |
| ИИ-секундант, проверка формулировки | `gpt-6.1-sol` | по запросу |

**Стоимость одной оценки со всеми вызовами ≈ $0.06–0.09** (замеры на 65 DEV-диалогах: только критерии с голосованием —
$0.056 на диалог, 56 с на весь набор; с разбором партии — ещё ≈ $0.01–0.03). Время: 6–25 с на диалог, параллельно по 10.
Цены: gpt-6.1-sol $2 / $10, gemini-3.8-flash $0.375 / $1.875 за 1M токенов;
счётчик в интерфейсе считает $ по фактическим токенам.

`temperature=0` модель gpt-6.1-sol не поддерживает — стабильность обеспечивают строгая JSON-схема,
перечисление допустимых ответов в схеме и проверка цитат. Провайдер меняется в `.env`
(`CRITERIA_PROVIDER=openai|gemini|groq`).

## Точность

Эталона для DEV организаторы не дали, поэтому мы вручную разметили все 65 диалогов строго по чек-листу
(`data/reference_raw.txt` — одна строка на диалог с пояснениями) и использовали разметку **только** для
измерения (`scripts/run_dev.py`). В систему эталон не подмешивается: каждая оценка — это реальные вызовы
модели по текущему чек-листу.

| Прогон | Совпадение по критериям | MAE итога | Итог совпал точно |
|---|---|---|---|
| v1 — промпты по тексту чек-листа | 89.2% | 8.56 | 37/65 |
| v3 — + правила применения (guidance) | 96.5% | 2.65 | 51/65 |
| v4 — то же + разбор партии (повтор) | 96.2% | 3.22 | 50/65 |
| v5 — повтор на финальной версии | 95.8% | 3.24 | 49/65 |
| **v6 — + голосование 3 оценок при уверенности < 0.95** | **96.5%** | **2.53** | **51/65** |

Отчёты: `data/runs/*/REPORT.md` (по каждому расхождению — эталон, ответ модели и её обоснование).

```bash
python -m scripts.run_dev                         # прогон DEV + отчёт по ошибкам и стоимости
python -m scripts.run_dev --only p1-ru-001 --annotations
python -m scripts.eval_one p1-kz-003              # один диалог с подробным выводом
python -m pytest -q                               # 37 тестов: подсчёт итога, цитаты, метрики, весь HTTP API (модель подменена)
python -m scripts.e2e_ui http://localhost:8000    # сквозной сценарий демо в браузере с настоящей моделью (10 шагов)
```

## Развёртывание и база данных

- Google Cloud Run + Cloud SQL одной командой: `GCP_KEY=gcp-key.json ./scripts/deploy_gcp.sh` (подробно — `docs/DEPLOY.md`).
- Без входа, но с защитой расходов: `DAILY_BUDGET_USD` (дневной потолок на модели) и `RATE_LIMIT_PER_MIN` (лимит оценок с IP).
- Аудит алгоритма, API и найденных проблем — `docs/AUDIT.md`.

## Как устроена оценка

1. Транскрипт нумеруется: `[i] (MM:SS от начала) РОЛЬ: текст`. Оценивается только оператор; бот и system —
   контекст (например, «Личность клиента подтверждена» — доказательство для идентификации).
2. **Отдельный вызов на каждый критерий** со своей формулировкой, условием N/A, шкалой и правилами применения.
   Схема ответа строится из чек-листа: модель физически не может выбрать N/A там, где он запрещён, или
   ступень, которой нет в шкале.
3. **Голосование**: если уверенность модели < 0.95 (на DEV такие ответы верны лишь в 68% против 99% при ≥ 0.95),
   критерий оценивается ещё дважды независимо, побеждает большинство. Голоса видны в карточке (🗳).
4. **Проверка доказательств**: каждая цитата должна дословно найтись в реплике с указанным индексом
   (с допуском на кавычки «»/"" и ё/е). Если найдена в соседней — индекс исправляется; если не найдена —
   повторный вызов с обратной связью (до 2 раз), затем флаг «низкая уверенность».
5. **Детерминированные метрики кодом**: время первой реакции (от перевода на оператора), паузы,
   доля речи оператора. Передаются модели как факты (порог первой реакции 3 мин).
6. **Подсчёт итога — чистая функция** (`backend/scoring.py`, тесты в `tests/test_scoring.py`): «Да» — полный вес,
   «Нет» — 0, шкала пропорционально весу (верхняя ступень = полный вес), вес N/A перераспределяется между
   применимыми критериями (максимум 100), округление до 2 знаков (ROUND_HALF_UP), грубая ошибка — отдельный флаг.
7. **Обучение на апелляциях**: в промпт критерия добавляются 3 последних решения проверяющего по нему
   (фрагмент, исходная оценка, решение, причина); апелляции по самому оцениваемому диалогу не используются.
8. Поддерживаются RU, KZ, EN и смешение языков; ошибки распознавания речи в звонках не наказываются.

## Функции

**Из задания:**
- Редактор чек-листа: критерии, формулировка, вес, тип (да/нет, шкала, флаг грубой ошибки), ступени шкалы,
  N/A и его условие, секции. Каждое сохранение — новая версия; любую версию можно выбрать для оценки.
- Оценка выбранного диалога выбранной версией чек-листа.
- Карточка результата: ответ, баллы, вес (и вес после перераспределения), обоснование, цитаты, проверенный
  участок для пропущенного действия, причина N/A, итог и секции. Клик по доказательству прокручивает
  к реплике и подсвечивает цитату; у звонка — перематывает плеер (с учётом пауз записи).
- Апелляция: критерий + комментарий. Проверяющий (отдельный экран) видит спорную оценку, комментарий и
  фрагмент, подтверждает или меняет с причиной; итог пересчитывается. В карточке: исходная оценка → решение →
  финальный результат.

**Наши:**
- **Живая оценка**: критерии появляются по мере готовности (SSE), рядом таймер и счётчик $.
- **Разбор партии**: знаки ходов у реплик оператора, «лучший ход» для `?` и `??`, eval bar настроения клиента,
  значки на дорожке плеера звонка.
- **ИИ-секундант**: рекомендация проверяющему по апелляции со ссылками на реплики.
- **Проверка формулировки критерия**: ИИ находит двусмысленности, предлагает формулировку и правило N/A.
- **Пробный запуск**: после изменения чек-листа — прогон на 5 разных диалогах (язык × канал) и таблица
  «было → стало»; переоцениваются только изменённые критерии.
- **Пакетная оценка**: одна кнопка «Оценить весь набор» для любого group_id — загрузка из API, параллельная
  оценка с прогрессом, повтор при сбое. Экспорт CSV (строгий режим / Dynamics 365).
- Интерфейс в стиле Apple: боковая панель, транскрипт пузырями как в мессенджере, раскрывающиеся критерии,
  RU / EN / KZ, светлая и тёмная тема, адаптив под телефон.
- Горячие клавиши: `J`/`K` — следующий/предыдущий диалог, `↑`/`↓` + `Enter` — критерии и переход к доказательству,
  `E` — оценить, `/` — поиск, `Esc` — к списку.

## Контрольный набор (за 1 час до стоп-кода)

1. Вкладка «Диалоги» → в поле «Набор» ввести новый `group_id` → Enter (набор загрузится из API).
2. «▶ Оценить весь набор» — 10 диалогов ≈ 1 минута, ≈ $0.5.
3. Если организаторы попросят заменить критерий: «Чек-лист» → изменить → «Проверить формулировку» →
   «Пробный запуск» → «Сохранить новую версию» → «Использовать для оценки» → снова «Оценить весь набор».

## Архитектура

```
backend/
  app.py          FastAPI: REST + SSE, раздача фронтенда
  engine.py       оценка диалога: вызовы по критериям, проверка цитат, разбор партии
  prompts.py      промпты и JSON-схемы (строятся из чек-листа)
  llm.py          единый адаптер OpenAI / Gemini (Vertex) / Groq, повторы, подсчёт стоимости
  scoring.py      подсчёт итога по правилам чек-листа (чистая функция)
  transcript.py   индексы, метрики, проверка цитат, смещения в аудио
  features.py     апелляции и пересчёт, ИИ-секундант, проверка формулировки, пробный запуск, аудио
  storage.py      SQLite: наборы, версии чек-листов, оценки, апелляции
  contract.py     контракт результата (Pydantic) → docs/contract.schema.json
  checklist_default.json  чек-лист из PDF организаторов + правила применения
static/
  index.html, css/app.css
  js/api.js       единственный модуль общения с бэкендом (базовый URL настраивается)
  js/components/  <cqa-list> <cqa-review> <cqa-appeal> <cqa-checklist-editor> — Web Components
```

**Встраивание в Dynamics 365**: каждый экран — самостоятельный Web Component без фреймворков. Достаточно
подключить `static/js/app.js` (или отдельный компонент) как веб-ресурс и задать `window.CQA_API_BASE`
на адрес бэкенда.

## API (кратко)

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/groups/{group_id}/sync` | загрузить набор из API организаторов |
| GET | `/api/conversations?group_id=` | список с последними оценками |
| POST | `/api/evaluate` | оценка диалога (SSE-поток событий) |
| GET | `/api/evaluations/{id}` | результат по контракту |
| POST | `/api/batch`, GET `/api/batch/{id}` | пакетная оценка и прогресс |
| GET/POST | `/api/checklists` | версии чек-листа / сохранить новую версию |
| POST | `/api/checklists/lint`, `/api/checklists/trial` | проверка формулировки, пробный запуск |
| POST | `/api/appeals`, `/api/appeals/{id}/decision`, `/api/appeals/{id}/second` | апелляции |
| GET | `/api/export.csv` | экспорт результатов |
